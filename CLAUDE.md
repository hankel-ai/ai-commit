# ai-commit

AI-powered git commit message generator with GUI and CLI interfaces.

## Tech Stack

- **Language:** Python 3.7+
- **GUI:** Dear PyGui 2.0+ (`dearpygui`)
- **System Tray:** pystray 0.19+
- **Icons:** Pillow 10.0+
- **Platform:** Windows 11 (primary), macOS/Linux supported

## AI Providers

- **Ollama** (default) — HTTP API to local/remote Ollama instance (`/api/chat`)
- **Kiro** — Native Windows `kiro-cli.exe` (**not** WSL). `resolve_kiro_cli()` looks at
  `AI_COMMIT_KIRO_CLI` (full path override) → `PATH` → known install locations
  (`%LOCALAPPDATA%\Programs\kiro-cli\`, `%LOCALAPPDATA%\kiro-cli\`, `…\Kiro\bin\`,
  `%USERPROFILE%\.local\bin\`, each also with a `bin\` variant), and raises a
  `KiroCliError` naming everywhere it looked. The prompt is fed to
  `kiro-cli chat --no-interactive --model <model>` on **stdin** — no temp file, no
  shell, no argument-length limit. Resolution always yields an **absolute** path,
  which matters on Windows: `subprocess` (CreateProcess) can launch a `.cmd`/`.bat`
  shim by full path but cannot find one via PATH lookup itself.

Default model: `qwen3-coder:480b-cloud` (configurable via settings or `AI_COMMIT_MODEL` env var)

## Deploy

`deploy.cmd` robocopies the project to `%USERPROFILE%\OneDrive\Programs\ai-commit` (where the startup shortcut points). **The user runs this manually — never invoke it from Claude Code.**

## Run / Build

Launchers use an **isolated venv OUTSIDE OneDrive** at `%USERPROFILE%\.venvs\ai-commit`
(avoids OneDrive sync churn). `g-ui.cmd` / `g.cmd` self-bootstrap it on first run
(create venv + `pip install -r requirements.txt`) and self-heal if a dep goes missing.
Never rely on system Python — a July 2026 global-Python reinstall wiped its packages
(see `python312-reinstall-wiped-global-packages` memory).

```bat
g-ui.cmd [folder...]   :: GUI (launches venv pythonw, windowless)
g.cmd [folder] [--provider ollama] [--model qwen3-coder:480b-cloud]   :: CLI
```

**Autostart:** the GUI auto-starts via HKCU `...\Run\AICommitMonitor`, which points
**directly** at `%USERPROFILE%\.venvs\ai-commit\Scripts\pythonw.exe ...\Programs\ai-commit\ai-commit-gui.py`
(bypasses `g-ui.cmd`, so the venv must already exist — run `g-ui.cmd` once after any venv wipe).

Raw (venv must exist): `%USERPROFILE%\.venvs\ai-commit\Scripts\python.exe ai-commit-gui.py`

## Architecture

- GUI runs a polling loop that discovers git repos **and non-git folders** in watched folders and checks for uncommitted changes
  - **Folded poll path** (perf): each repo's live poll runs a single `git status --porcelain --branch` via `ai_commit_core.read_status_branch` + `parse_branch_header`, which yields dirty entries, current branch, ahead/behind, and the branch's local-only/stale classification in one spawn (was 4 separate git calls; ~4.7× faster — 9→2 spawns/repo/cycle). The GUI helper `_read_poll_status(rp, remote_url, do_fetch)` wraps it (optionally `fetch_remote` first) and feeds all three poll sites (`_poll_one_repo`, `bg_refresh_single_repo`, `bg_refresh_then_generate`). Covered by `tests/test_status_branch.py`. **Full analysis + the 5 considered options (incl. the deferred FS-watcher ideas) live in `docs/polling-performance.md`** — read that before further poll-perf work.
  - **Paused fast-path**: when globally paused (and not a manual Refresh), `bg_poll_repos` skips the folder rescan entirely — it iterates only the already-known `app.repos`, runs a live `_poll_one_repo` for force-active repos and reuses `_cached_repo_result` for the rest. Avoids a `git rev-parse` (via `is_git_repo`) on every repo each cycle just to rediscover them. New repos surface on Unpause or Refresh. Per-repo poll/cache logic is factored into `_poll_one_repo` / `_cached_repo_result`, shared with the normal discovery loop. Covered by `tests/test_poll_pause.py`.
- **Startup fan-out (parallel poll)**: `trigger_poll` submits `bg_poll_repos` as a **single** task and its per-repo loop was serial, so raising the module `executor`'s `max_workers` did nothing for poll speed — a 50-repo launch took ~70 s, ~68 s of it network I/O (`git fetch` + `gh repo view` per repo) waited on one at a time. `bg_poll_repos` now runs **discover → decide → execute**: the decision pass only classifies each repo (pause / idle-tier / force rules unchanged) into a `live` list, then `_run_poll_batch(live, force)` polls them concurrently on a **short-lived** `ThreadPoolExecutor(min(app.poll_threads, len(live)))` created and torn down per cycle; `_map_is_git_repo` does the same for discovery's `git rev-parse` probes. **Never fan out onto the module-level `executor`** — it has 4 workers and already holds this task, so two overlapping polls (auto cycle + manual Refresh) would each occupy a worker and then block on subtasks that can never be scheduled. A repo that raises falls back to its cached result instead of killing the cycle (the old loop had no guard: one unreadable repo meant no `poll_result` at all and a UI stuck on `...`). Width is the **`poll_threads` setting** (default 8, clamped to `POLL_FANOUT_MAX`=16, Settings→Polling): measured on Windows, network calls plateau at ~3–3.5× by 4–8 threads and local git barely scales — **process spawn, not bandwidth, is the limit**, so past ~8 is dead weight. Measured on the real watched folders: serial 59.2 s → **17.3 s** (3.4×), parity-checked at 0 mismatches across 50 repos × 10 result fields. Covered by `tests/test_poll_parallel.py` (real threads + a `threading.Barrier`, so a serial implementation fails instead of quietly passing). Full numbers in `docs/polling-performance.md`.
- **Streaming poll (each repo renders as it lands)**: `_run_poll_batch` used to return only once every future had resolved, and `bg_poll_repos` posted a single `poll_result` after that — so the whole list waited on the slowest repo. With unreachable remotes that is the full stall-watchdog wait (~20 s each, `poll_threads` at a time) staring at `...` for repos that answered in milliseconds. `_run_poll_batch(live, force, on_result=None)` now calls `on_result(repo_key, info)` from its `as_completed` loop the moment each repo finishes — **including a repo that raised with no cache to fall back on** (`info=None`), or its placeholder would stay pending for the rest of the cycle. `bg_poll_repos` posts `_post_poll_stream(pending, results, non_git)` once up front (everything already known — cached / idle-tier / paused repos and the non-git folders render immediately) and then feeds `_poll_streamer(pending)` to the batch, which posts one `poll_stream` message per arrival carrying `{repo_key: info}` plus a **snapshot** of the shrinking pending set (the live set keeps being mutated on the pool's completion thread; the UI thread must never see it change underneath).
  **The final `poll_result` is unchanged and stays authoritative** — streaming is purely additive, so pruning, `clear_errors`, the visibility-cache flush and `last_results`/`last_non_git` all still happen exactly once per cycle. Its handler also clears `poll_pending` / `poll_stream_dirty` so a stale streaming repaint can't land after it and resurrect a half-finished list.
  **Repaints are coalesced, not per-message.** `rebuild_repos_ui` tears down and rebuilds the whole list, so repainting per arriving repo would be O(n²) on a 50-repo launch. The `poll_stream` handler only merges into `app.last_results` and sets `poll_stream_dirty`; `process_queue` repaints **once after the queue drains**, and at most every `POLL_STREAM_INTERVAL` (0.25 s). Streaming repaints pass `preserve_open=True` so headers stay as the user left them mid-cycle; the final `poll_result` reapplies the activity default.
  `rebuild_repos_ui` takes `pending=` and renders a dim `name  ...` row for each pending repo not yet in `results` — it clears `repos_container` wholesale, so without that a mid-cycle repaint would erase the placeholders `repo_loading` put there and repos would blink out of the list until their own poll returned. Pending rows are never counted as `hidden`. Covered by `tests/test_poll_streaming.py` (real threads + a real `Event`: the fast repos are asserted reported **while the slow one is provably still blocked**, so a collect-then-report implementation fails; plus a real Dear PyGui render for the placeholder row).
- **Repo visibility cache**: `get_repo_visibility` shells out to `gh repo view` (~440 ms of network, and **invisible in the activity log** — it uses `subprocess.run`, not `run_git`) and was cached only on `RepoState`, which starts empty, so ~50 remotes cost ~22 s on **every** launch for a badge that never changes. `AppState.visibility_cache` (`repo_key -> "PUBLIC"/"PRIVATE"/""`) now persists in the settings JSON; `_repo_visibility_cached` resolves session state → cache → gh. **Membership, not truthiness, is the hit test** — a cached `""` (GitLab remote, no remote, gh missing) has to stick or those repos re-pay every launch. `repo_force` (manual Refresh / force-active) re-asks and overwrites. Poll workers only set `visibility_cache_dirty`; the `poll_result` handler prunes unwatched keys and calls `_save_settings()` **on the main thread** — saving reads `dpg.get_viewport_pos()` and must not run in a worker. Second launch: 17.3 s → **14.8 s**. Covered by `tests/test_visibility_cache.py`.
- **Recency tier (visibility + poll cost)**: repos are classified Active vs Idle by the pure `ai_commit_core.is_repo_active(commit_ts, dirty, ahead, behind, now, recent_days)` — Active = dirty OR ahead/behind OR last commit within `recent_days`. **Active** repos poll every `poll_interval` (120s) and show; **Idle** repos (clean, synced, old) are hidden by the recency filter and polled only every `idle_poll_interval` (default 900s). The tiered gate lives in `bg_poll_repos`' normal loop: a known Idle repo whose last live poll (`app.idle_last_poll[repo_key]`, stamped on **every** live poll) is within `idle_poll_interval` reuses `_cached_repo_result`; new repos, manual **Refresh** (`force=True`), and force-active overrides always poll live. Display filter is applied in `rebuild_repos_ui`'s render loop (skips `build_repo_section` for Idle repos unless force-active or sticky-error; sets `hidden_count_label`); the raw poll payload is cached (`app.last_results`/`app.last_non_git`) so toggling **Recent only** re-renders with **no** git work. `get_last_commit` now returns a 3rd value `commit_ts` (epoch) carried through the result dicts / `RepoState.last_commit_ts` / `_cached_repo_result`. **Timezone**: `git log --format=%ci` prints the committer's *own* zone with an offset (`2026-07-20 21:30:00 +0530`); the pure `ai_commit_core.parse_commit_date` honours that offset and re-renders in the **viewer's** local zone. Dropping the offset (the old behaviour) made commits pushed from another zone — e.g. GitLab colleagues in IST, CI runners on UTC — display as *future* timestamps and skewed `commit_ts` for the recency window. Covered by `tests/test_commit_date.py` (all assertions are tz-independent). Settings: `recent_only` (bool, toolbar + Settings→Display checkboxes), `recent_days` (int, default 14), `idle_poll_interval` (int secs, default 900). **Non-git folders** get the same recency filter via the pure `ai_commit_core.is_folder_recent(mtime, now, recent_days)` — the folder's `stat().st_mtime` (stamped into the poll payload / `NonGitFolder.mtime`) stands in for git signals; unknown mtime (0.0) always shows. Hidden non-git folders count into `hidden_count_label` (only when `show_non_git_folders` is on) and stay in `app.non_git_folders`. This replaces the old manual "move idle repos into a `_idle_projects_*` subfolder" workaround (discovery is still one level deep, so that trick still works too). Covered by `tests/test_recency.py` (pure predicates). See `docs/polling-performance.md` for the poll-cost background.
- **Header expand/collapse**: `ai_commit_core.compute_header_open` is the single pure decision (unit-tested in `tests/test_header_open.py`). Full refreshes (poll loop / Refresh-all) use `preserve_open=False` → activity-based default. Partial rebuilds (single-repo refresh, refresh-then-generate) use `preserve_open=True` → keep each header's prior open state so other repos don't auto-collapse. Two per-repo opt-outs override `preserve_open` for one rebuild: `app.expand_on_next_build` / `force_expand` (force open even when paused, e.g. single-repo Refresh) and `app.collapse_on_next_build` / `force_collapse` (re-apply the activity default so a now-idle repo collapses — set after a successful **Commit & Push** so the just-pushed repo doesn't stay stuck expanded).
- **Sticky errors**: a repo's `GenStatus.ERROR` (e.g. push failure) survives rebuilds (`rebuild_repos_ui` sticky-error branch) so polls don't wipe it. It is cleared by: Refresh-all (`poll_result` plumbs `force` → `clear_errors`), a force-active repo's poll, or a **manual per-repo Refresh** — `bg_refresh_single_repo(force=True)` carries `force` in the `single_repo_refresh` queue message and the handler resets that one repo's error before rebuilding. Automatic single-repo refreshes (post-commit, branch ops, `force=False`) never clear errors. Covered by `tests/test_single_refresh_error.py`.
- **Secret-push-protection override**: when a push is rejected by GitLab's secret push protection (pre-receive prints "PUSH BLOCKED: Secrets detected" + suggests `-o secret_push_protection.skip_all`), `is_secret_push_block` (in `ai_commit_core`) detects it in both failure paths (`commit_result` push error and `push_upstream_result`) and auto-shows `_show_secret_push_prompt` — a red-warning popup offering "Push Anyway (skip protection)". Confirm runs `bg_push_override` (`git push -o secret_push_protection.skip_all`, plus `--set-upstream origin <branch>` if the blocked push was the set-upstream one; `push_upstream_result` messages carry the branch as an optional 5th element). Cancel leaves the sticky error as-is. Result is posted as `push_upstream_result`, reusing its success flow (status, collapse, refresh, Actions viewer). Covered by `tests/test_secret_push_override.py`.
- **Push-rule rejection (declined, and NOTHING bypasses it)**: GitLab declines a push through the *same* `pre-receive hook declined` line for two unrelated reasons, and only one of them has a bypass. Secret push protection does (`-o secret_push_protection.skip_all`, above); a **push rule** — prohibited file name, commit-message regex, max file size, author email — does **not**, and neither does GitHub's protected-branch hook. Widening `is_secret_push_block` to cover them would offer a "Push Anyway" button that can only ever fail, so `ai_commit_core.is_push_rule_block(stderr)` is a *separate* predicate: it matches `hook declined` / `hook refused` and **excludes** anything `is_secret_push_block` already claims, so the override path keeps priority. Both failure handlers (`commit_result`, `push_upstream_result`) test it as an `elif` after the secret check and show `_show_push_rule_prompt` — a popup with **no retry button**, carrying `ai_commit_core.remote_reject_reason(stderr)` (the `remote:` lines with the prefix and the bare `GitLab:` banner stripped, falling back to the raw text so it is never empty — that is the only half of the failure that says *which* rule and *which* file), an explicit "this is not secret push protection, no push option bypasses it", and a **Copy Error** button for the raw stderr. When the blocked push carried `--set-upstream`, the popup also states that `origin/<branch>` was **not** created: the ref update is refused whole and git leaves the local tracking config untouched, so the repo is exactly where it started. The rule-block branch also pre-empts the `needs_upstream_setup` fallback below it, which would otherwise re-offer the set-upstream prompt for a push that already reached the remote. Real case that motivated it (dxacontainerize, 2026-09-02): `File name helm/charts/apphost/secrets/dev/dfc.keystore was prohibited by the pattern ...` rendered as a dead-end sticky error with the reason clipped off the panel edge. Covered by `tests/test_push_rule_block.py` (predicates, both handler routings, a regression guard that the secret block still wins, plus a **real Dear PyGui render** of the popup wording).
- **Sticky errors are hard-wrapped, not dpg-wrapped**: the repo status line is created with `wrap=0`, which does **not** break a single very long line here — a one-line remote rejection ran off the right edge of the panel with the reason unreadable and no way to scroll to it. Both writers (`update_repo_status` and the sticky-error branch of `build_repo_section`) now pass the text through `_wrap_for_display`, the same viewport-width-derived hard wrap the commit-message box uses, so it re-wraps on resize instead of being pinned to a hardcoded pixel count.
- **Push-only retry (unpushed commit, clean tree)**: push used to exist *only* as the tail of `do_commit_and_push`, reachable *only* via the **Commit & Push** button — which `build_repo_section` renders inside `if rs.entries:`. So when a commit landed but its push failed (transient remote error such as GitHub's `remote: Internal Server Error`, dropped connection, or a commit made outside the GUI), the tree was clean, `rs.entries` was empty, no button row rendered at all, and the `PUSH REQUIRED` banner was bare text — a dead end that a manual Refresh only re-rendered. The banner now carries a **Push** button (mirroring how the `behind > 0` banner carries **Preview Pull**); it is placed on the banner deliberately, since that block renders *above* the `if rs.entries:` split and so covers clean **and** dirty trees. Visibility is the pure `ai_commit_core.should_offer_push(ahead, behind, remote_url)` — needs a remote, `ahead > 0`, and `behind == 0` (when behind, a plain push is non-fast-forward, so Preview Pull is offered instead). `cb_push_now` → `bg_push_only` runs a bare `git push` and posts `push_upstream_result`, reusing that handler's success flow (status, collapse, refresh, Actions viewer) and failure flow (sticky error + secret-block prompt); it sends an empty branch so a secret-block override retries with a plain push, never `--set-upstream` (a branch with no upstream fails `NO_UPSTREAM:` earlier and takes `_show_upstream_prompt` instead). Covered by `tests/test_push_only.py` (predicate + background task) and `tests/test_push_button_render.py` (**real Dear PyGui render** — creates a context without a viewport, builds a section, walks the item tree for button labels; the predicate test alone cannot catch a button that was never wired in. Self-skips if a dpg context can't be created).
- **Upstream-name mismatch (push refused, no prompt)**: git has **two** refusals for "this branch has no same-named remote branch to push to", and only the first used to reach the "Push & Set Upstream" prompt: (1) `fatal: The current branch X has no upstream branch.` and (2) `fatal: The upstream branch of your current branch does not match the name of your current branch.` — what push.default=simple says when the branch tracks a *differently named* remote branch (branched off a remote-tracking ref, or `branch.autoSetupMerge=always`). Case (2) fell through to a bare sticky error with no button, so a branch whose remote counterpart didn't exist yet (seen on GitLab: local `main_master` tracking `origin/zulu_master`) could not be pushed from the GUI at all. Detection is now the pure `ai_commit_core.needs_upstream_setup(stderr)`, which covers both wordings — it flattens whitespace first because git **hard-wraps message (2) mid-sentence**, so no phrase spanning the wrap is contiguous in the raw text. `parse_upstream_mismatch(stderr)` pulls the differently-named upstream out of git's own `git push origin HEAD:<name>` suggestion line. Both failure paths use it: `do_commit_and_push` returns `NO_UPSTREAM:<branch>[:<mismatched upstream>]` (`:` is illegal in a git ref name, so the split back apart is unambiguous), and the `push_upstream_result` failure handler — the path behind the banner **Push** button, which previously only checked for a secret block — now shows `_show_upstream_prompt` too. That prompt takes `current_upstream=` and, when set, says what the branch tracks today and that confirming repoints it, instead of the false "has no remote tracking branch". **Loop guard**: the handler only prompts when the failed push carried an *empty* branch (5th message element) — a non-empty one means the failure already *was* the `--set-upstream` push. Covered by `tests/test_upstream_mismatch.py` (verbatim git stderr for both wordings, `do_commit_and_push` classification, all four handler branches, plus a **real Dear PyGui render** of the popup wording).
- **EOL-only changes (dirty status, empty diff)**: with git check-in normalization on (`core.autocrlf=input`/`true`, or a `* text=auto` .gitattributes rule), a file whose only change is CRLF↔LF is listed by `git status --porcelain` as ` M` but yields an **empty** `git diff HEAD` / `--stat` / `--name-only` — git converts the working copy back to the committed blob, so `git commit` would say "nothing to commit". `get_diff` therefore returned `""` and Generate reported a bare "No diff content available."; `ai_commit_core.describe_empty_diff(cwd, only_path=None)` now explains it instead (which file, `LF committed, CRLF on disk`, the effective `core.autocrlf`, and the fix: mark the path `-text` in `.gitattributes` + `git add --renormalize .` — verified that `text eol=lf` does **not** change the blob, it only controls checkout). Used by `bg_generate_message` and `bg_launch_diff_viewer`. Detection = `normalizes_to_same_content` (covers the byte-identical `autocrlf=true` case, where the blob is LF and only the expected *checkout* is CRLF) **plus** an empty per-file `git diff HEAD --` guard so mode-only changes aren't mislabelled. Reading blobs needs `run_git_bytes` — plain `run_git` is text-mode, and universal newlines would rewrite the very CRLFs being inspected (`run_git`/`run_git_bytes` now share `_run_git`). The repo status line is `wrap=0` so the multi-line explanation wraps. Covered by `tests/test_eol_only.py`.
- **Init on a folder git refuses to read (dubious ownership)**: `git init` returns **0** in a directory whose *owner* isn't the current user, but every command afterwards exits 128 -- including the `rev-parse --show-toplevel` behind `is_git_repo`. The folder therefore re-rendered as "not a git repo" with an Init button, so Init looked like a no-op and stayed clickable forever (seen on `ClaudeCode\cc-tmux`: 3 × `git init` rc=0 against 314 × `rev-parse` rc=128 in the activity log). On Windows a folder created by an **elevated** process is owned by `BUILTIN\Administrators` (SID `S-1-5-32-544`) even when its contents are user-owned; git's safe.directory check only waives an Administrators-owned path when the *reading* process is itself elevated (`IsUserAnAdmin()`), which the GUI never is. `bg_git_init` now calls `ai_commit_core.verify_repo_usable(cwd)` after a zero-exit init and posts the failure instead of a bogus success; `is_dubious_ownership` / `describe_dubious_ownership` turn git's five-line fatal into the two real fixes (`icacls <dir> /setowner "%USERDOMAIN%\%USERNAME%"`, preferred, or a `safe.directory` exception). The non-git status line is `wrap=0` so that explanation wraps. Covered by `tests/test_dubious_ownership.py`. Note this state can't be reproduced from a non-elevated shell -- Windows rejects *assigning* Administrators as an owner ("This security ID may not be assigned as the owner of this object"), so the ownership-refusal path is tested by stubbing `run_git`.
- **Bulk pull (toolbar "Pull" button)**: pulls every repo that is safe to pull, in one gesture. **Two-phase**: `cb_pull_all` sets `app.show_pull_prompt_on_next_poll` and runs a forced `trigger_poll(force=True)`; the `poll_result` handler then shows the prompt. The refresh is not optional — eligibility depends on `behind`, which is only accurate right after a fetch, so prompting from cached counts would offer repos with nothing to pull and miss ones that have changes. Eligibility is the pure `pull_all_eligible(repos)` → `(eligible, dirty_count)`: **clean AND behind** (`not rs.entries and rs.behind > 0`). Dirty is excluded (pulling into a dirty tree risks a conflicted merge); already-synced is excluded (a `git pull` there is a pointless network round trip). Nothing eligible → a notice modal that distinguishes the three reasons (no repos watched / all dirty / all up to date), never a dead confirm dialog. `_cb_confirm_pull_all` **re-validates** eligibility before acting, since the dialog can sit open across a poll cycle.
  **The batch runs on ONE worker** (`bg_pull_all`, sequential), *not* one `executor.submit(bg_pull, ...)` per repo. `executor` has 4 workers and also serves the poll and every UI action; N concurrent `git pull`s — each allowed up to `GIT_TIMEOUT_NETWORK` (300 s) — occupy all of them and the app stops responding until they drain. That fan-out is what froze the GUI on the first cut of this feature.
  Per-repo progress posts `pull_all_status`; a failure posts `pull_all_failed`, which sets a **sticky** `GenStatus.ERROR` — a plain status line would be wiped by the very next repo's refresh rebuild.
  **Why the status writes are all guarded**: `build_repo_section` reassigns `rs.status_tag`, but `rebuild_repos_ui` only calls it for repos it actually renders — and a just-pulled repo becomes clean+synced+old, so the recency filter (**on by default**) hides it and its `status_tag` keeps naming the text item the *previous* render created, which died with `repos_container`. Writing to a destroyed item id **crashes** Dear PyGui rather than no-opping; that was the crash on confirm. `update_repo_status` now returns early on a dead tag (it is called from many places, all exposed to the same hazard) and the `pull_result` handler is guarded the same way. Covered by `tests/test_pull_all_render.py` (pure eligibility + a real Dear PyGui render of both the confirm and notice branches).
- **Toolbar renames**: "Add Folder" → "+" (with tooltip "Add Folder"), "Activity Log" → "Activity" (with tooltip "Activity Log"), to reclaim space for the new Pull button. Tooltips mirror the existing pattern on the Date/Recent filter checkboxes.
- **Preview Pull commit/file diffs**: the Preview Pull window lists each incoming commit and each incoming file as its own row with a **View Diff** button, instead of the two read-only text blobs it used to show. `get_incoming_changes` therefore returns **structured** data — `(upstream, commits, files)` where `commits` is `[{"sha","subject","date","ts"}]` and `files` is `[{"path","old_path","added","deleted","binary"}]` — fed by two pure parsers, `parse_incoming_log` (from `git log --format=%h%x00%ci%x00%s`, NUL-delimited so odd subjects can't break the split; subject comes **last** with `split("\0", 2)` so it is taken verbatim to end of line) and `parse_numstat_z` (from `git diff --numstat -z`). Each commit row shows its timestamp, run through the shared `parse_commit_date` so it renders in the **viewer's** zone in the same `Jul 29 08:36am` format as the repo header — a commit from a UTC CI runner or an IST colleague must not read as hours in the future (same reasoning as the Recency-tier note above). **The `-z` form is load-bearing**: plain `--numstat` renders a rename as `a/{b => c}/d`, which is *not* a valid pathspec, so that row's View Diff button would fail; with `-z` a rename is an empty path field followed by two more NUL fields (old, new) and `path` resolves to the new name. Clicking a commit runs `get_commit_patch` = `git show --first-parent --patch --stat <sha>` — **`--first-parent` is required** because plain `git show` on a merge prints the message and *no patch at all*; if the body still has no `diff --git` it falls back to `git diff <sha>^1..<sha>`. Clicking a file runs `git diff HEAD...<upstream> -- <path>` (the net incoming change across all incoming commits). All three diff producers (local file, incoming commit, incoming file) share `_spawn_diff_viewer(title, diff_text)` in the GUI. Failures now post a distinct `preview_pull_error` queue message (the old code stuffed the exception into the diffstat slot, so errors rendered as if they were content). Covered by `tests/test_incoming_preview.py`.
- **diff_viewer.py payload**: `{"title": <header>, "diff": <patch>}`; `filepath` is still accepted as a fallback for `title`. It renders **one `dpg.add_text` per line**, so it caps at `MAX_LINES = 4000` and appends a truncation note — a whole commit's patch (lockfile, squash merge) would otherwise freeze the window on build.
- Background tasks (generate, commit+push, pull, poll) run in a `ThreadPoolExecutor` and post results to a `queue.Queue`
- Main thread processes the queue each frame and updates Dear PyGui widgets
- `RepoState` dataclass tracks per-repo UI state (tags, entries, status, messages); `NonGitFolder` dataclass for non-git directories
- Settings persist to `ai-commit-gui-settings.json` in project root
- **No git command can hang the app** (`_run_git`): the startup freeze was `git fetch` blocking forever. The first poll fetches every *new* repo (`do_fetch=is_new or repo_force`), and against a remote that accepts the TCP connection but never answers — a black-holing corporate proxy, a down VPN gateway — `git fetch --prune --quiet` never returns. `_run_poll_batch` joins all its futures, so **one** stuck fetch means `poll_result` is never posted and *every* repo sits on `...` (the repo names still render, because `_poll_one_repo` posts `repo_loading` before fetching); worse, that poll worker is gone permanently, so the pool bleeds threads until nothing polls at all. The `_run_poll_batch` fallback only catches repos that **raise** — a hang throws nothing. Two layers, both measured against a real black-hole listener:
  1. **git polices itself** via `_git_env()`: `GIT_HTTP_LOW_SPEED_LIMIT=1` + `GIT_HTTP_LOW_SPEED_TIME=20` is curl's stall watchdog and aborts a dead connection with a real error message and a clean process exit; `GIT_TERMINAL_PROMPT=0` plus `stdin=DEVNULL` closes the *other* hang shape — git asking for credentials under `pythonw.exe`, where there is no console to answer on; `GIT_SSH_COMMAND` adds `BatchMode=yes -o ConnectTimeout=10` for SSH remotes. Every value is a `setdefault`, so an operator override wins.
  2. **A hard timeout backstop** for what layer 1 can't see (a connect that never completes). **`subprocess.run(timeout=...)` does NOT work here** — measured: it kills `git.exe`, then blocks forever in `communicate()` because `git fetch` runs its transport as a separate `git remote-http` **grandchild** that inherited the stdout/stderr pipe handles and keeps them open. `_run_git` therefore uses `Popen` + `_kill_git_tree` (`taskkill /F /T /PID` on Windows, `killpg` elsewhere via `start_new_session=True`), and reports `GIT_TIMEOUT_RC` (124) with an explanatory stderr so the failure shows up as a red row in the Activity Log instead of silence.
  Budgets: `GIT_TIMEOUT_LOCAL` 60s, `GIT_TIMEOUT_NETWORK` 300s (chosen by `git_subcommand()`, which skips global options so `git -c x=y pull` isn't read as subcommand `x=y`), and `GIT_TIMEOUT_POLL_FETCH` 60s for `fetch_remote` specifically — it runs on a poll worker for every new repo, so it must give the worker back promptly; the repo just keeps its last known ahead/behind until a later cycle succeeds. `run_git` / `run_git_bytes` take an optional `timeout=` override. Covered by `tests/test_git_timeout.py`, which stands up a real socket server that accepts and never replies and runs every case on a watchdog thread, so a regression **fails** rather than hanging the suite.
  **Diagnosing a slow first poll:** the Activity Log now names the cause — rc=128 `Operation too slow` (dead/black-holed remote), rc=128 `could not read Username` (auth, `GIT_TERMINAL_PROMPT=0` doing its job), rc=124 `timed out` (connect never completed).
- **Concurrency safety**: `run_git` serializes per repo dir via a `threading.Lock` registry (`_repo_lock`) — the 4-worker pool + poll loop could otherwise collide on a repo's `index.lock`. `read_status(cwd)` returns `(ok, entries)` so callers can tell a git **failure** (`ok=False`) from a **clean tree**; `get_status` still returns `[]` for both (back-compat). Destructive flows (switch/create branch) use `read_status` and **abort** if `ok=False` rather than treating a failed status as clean — that bug previously let a status read losing an `index.lock` race bypass the confirm gate and switch branches without stashing. Covered by `tests/test_status.py`.
- **GitHub Actions viewer**: after a successful push, a background thread polls the GitHub API for workflow runs matching the pushed commit SHA (up to 30s). If runs are found, launches `gh_workflow_viewer.py` as a separate OS window (`subprocess.Popen` with `pythonw.exe`). If no runs exist (repo has no workflows, or push didn't trigger any), no window opens. The payload (which includes the gh auth token) is piped to the viewer via **stdin** (`argv[1] == "-"`), never written to disk; a temp-file path in `argv[1]` is still accepted as a legacy fallback. The viewer shows a tabbed UI with one tab per run, collapsible per-step sections with status icons and duration, and per-tab "Open on GitHub" / "Cancel Run" buttons. Logs are fetched per-job as each job completes (GitHub REST API only serves logs for completed jobs), with a final zip download pass to fill in any gaps (e.g. "Post Run" steps). Uses `gh auth token` for authentication.
- Setting `actions_popup_enabled` (default true) toggles the feature; stored in `ai-commit-gui-settings.json`
- **Activity Log**: every git command run under the hood flows through `ai_commit_core.run_git`, which calls an optional logger hook (`set_git_logger`). At startup the GUI calls `activity_log.clear_file()` + `install_git_logger()` so all git commands plus high-level events (generate/commit/push/pull) are written as JSON Lines to `%TEMP%/ai-commit-activity.jsonl`. The "Activity Log" toolbar button launches `activity_log_viewer.py` as a separate process that tails that file live (category filters, search, auto-scroll, pause, clear-view, **copy**: right-click any row → "Copy line", or the toolbar "Copy all" button copies all currently-visible/filtered rows as plain text via `dpg.set_clipboard_text`). The core stays decoupled — it only knows about the optional callback, never imports `activity_log`.
- **Smart display**: GitHub account only shown in repo header when it differs from active `gh` CLI user. Your global git identity is shown once in the top toolbar (`get_git_global_user`, a single read at startup). (Per-repo git identity probing — `get_git_user`, the effective-vs-global `!! Using different identity` header warning, and the `--local` override panel — was removed: it ran `git config user.name`/`user.email` on every repo each poll, flooding the activity log for no displayed value.)
- **MORE panel**: lazy-loaded per-repo panel showing gitignored files, **new-branch creation**, branch switcher, branch deletion, and GitHub Actions workflow dispatch
  - **New branch**: input + "Create" runs `git switch -c <name>` off current HEAD and switches to it. Duplicate names are pre-checked against the loaded local-branch list; other invalid names surface git's stderr. Before creating, `bg_create_branch` runs a live `read_status` (not the cached/Paused poll) and aborts if the tree can't be read; if the tree is dirty it posts `create_branch_needs_confirm` so the UI warns ("N changes will move to '<name>'") before proceeding. Follows the same fetch→build→callback + two-phase-confirm pattern as Delete branch. Note: Create **carries** uncommitted work (incl. untracked) onto the new branch by design — contrast Switch, which **isolates** it.
  - **Switch branch**: `bg_switch_branch(repo_key, label, args, confirmed=False)` isolates uncommitted work via a branch-tagged autostash. It reads the tree with `read_status` and **aborts** if git can't be read (never treats a failed status as clean). If the source tree is dirty (on a named branch) and unconfirmed, it posts `switch_branch_needs_confirm` first ("N changes on '<source>' will be stashed"). On proceed it runs `git stash push --include-untracked -m ai-commit-autostash:<source>`, then checkout — rolling the stash back if checkout fails. On arrival it pops the topmost `ai-commit-autostash:<target>` stash, but only onto a clean tree and never forcing a conflicted pop (stash kept + status message otherwise). Clean tree / detached HEAD → plain switch, no stash, no prompt. Pure lookup helper `find_autostash_ref` lives in `ai_commit_core.py` (unit-tested in `tests/test_autostash.py`, runnable via `python tests/test_autostash.py`).

- **Git Proxy (LAN, read-only)** — `git_proxy.py`, off by default, Settings → *Git Proxy (LAN)*. Turns the app into a **git remote** for every repo it watches, so another machine on the network can `git clone http://<this-pc>:8418/<repo>.git` and `fetch`/`pull` from it: no GitHub repo for things that don't need one, no `scp`-ing folders for a one-line change.
  **Fetch half only.** `git-receive-pack` is never spawned and both its endpoints answer 403, so a push is refused at the *protocol* level, not by policy — nothing on the LAN can write into a working repo the user is about to commit. There is no dumb-HTTP fallback either (it would hand out raw object files without ever going through upload-pack).
  **Two endpoints**: `GET /<slug>[.git]/info/refs?service=git-upload-pack` returns `pkt_line("# service=git-upload-pack\n") + "0000"` followed by the raw stdout of `git upload-pack --stateless-rpc --advertise-refs`; `POST /<slug>[.git]/git-upload-pack` pipes the request body into `git upload-pack --stateless-rpc` on stdin and streams stdout back. `GET /` is a plain index page listing every served repo with its clone URL (built from the request's `Host`, so it is correct behind a reverse proxy). Protocol v2 is honoured by forwarding the `Git-Protocol: version=2` header as `GIT_PROTOCOL` into the child env; without it clients silently fall back to v0.
  **The response is chunked, never buffered** — its length is unknown and a clone can be hundreds of MB. Request bodies must be de-chunked *and* gunzipped: git uses `Transfer-Encoding: chunked` and `Content-Encoding: gzip` depending on request size, and a server that only reads `Content-Length` works right up until a repo has enough refs to cross the threshold.
  **It does NOT use `run_git`.** That helper buffers all output, takes no stdin, and holds `_repo_lock(cwd)` — which would block the poll loop for the entire duration of a clone. `git_proxy` uses `Popen` directly but reuses `ai_commit_core._git_env()` and `_kill_git_tree()` (via a `threading.Timer` backstop, `UPLOAD_PACK_TIMEOUT` 900 s). Per-repo locking is deliberately *not* taken: upload-pack is a read, and git handles a ref moving mid-fetch on its own. **stderr is drained on its own thread** — reading it after the stdout loop deadlocks the moment git writes more than a pipe buffer of diagnostics.
  **Slugs** come from `RepoIndex`, rebuilt from `ai_commit_core.discover_repos()` over `app.watched_folders` with a 5 s cache (a clone makes 2-3 requests). Slug = repo directory basename; only *colliding* names get the longer `<parent>/<name>` form, so the common case stays short. Lookup is case-insensitive and `.git` is optional. **Path traversal is structurally impossible**: a request path is only ever *looked up* in that map, a filesystem path is never built from client input. The index is the live scan, not a startup snapshot, and it ignores the **Recent only** display filter — a display preference must not change what is fetchable, or an idle repo would start 404ing the day it ages out.
  **No auth by design** (the user fronts it with lanward/Traefik). The only gate in-process is `is_lan_client` — loopback, RFC1918, link-local, ULA, and Tailscale's 100.64/10. It reads the **socket peer only**: `X-Forwarded-For` is client-controlled, and behind a reverse proxy the proxy is the real boundary anyway (every request then arrives from the Traefik node and passes this check regardless of the true client). If that reverse proxy carries an **Authentik/SSO gate it will break git** — the ForwardAuth 302 comes back as login HTML and git reports "server does not support this protocol"; use a Traefik `basicauth` middleware instead, which git speaks natively.
  **Lifecycle**: `_apply_git_proxy()` in the GUI is the single place the server starts or stops, so the setting takes effect immediately with no restart (it also handles a port change by rebinding). It is **main-thread only** — it writes the Settings status line — and the server thread must never touch dpg or `_save_settings()`. `allow_reuse_address` is forced **off on Windows**, where SO_REUSEADDR lets a second process bind a port already in use and silently steal connections instead of reporting it. `handle_error` swallows ConnectionReset/BrokenPipe (a git client closing a keep-alive connection does this every time) so socketserver doesn't print a traceback to a stderr that doesn't exist under `pythonw.exe`.
  **Windows Firewall**: a new inbound listener under `pythonw.exe` is typically blocked with no visible symptom — it just looks unreachable from the LAN. Verify with `Get-NetFirewallRule`; the rule is the operator's to create.
  Covered by `tests/test_git_proxy.py` (real repos, a real server, and the real `git` binary as the client — clone, `.git`-less URL, protocol v2, pull-a-new-commit, push refused end-to-end, 404/403 shapes, advertisement bytes, stop/restart, busy port; every network call on a watchdog thread) and `tests/test_git_proxy_settings.py` (**real Dear PyGui render** of the Settings section plus a real toggle that must actually open and close a socket — the protocol suite cannot catch a checkbox that was never wired in).

## Security hardening (fix/security-hardening)

- **Diff privacy**: `get_diff` withholds the content of untracked files whose basename matches `SENSITIVE_FILE_PATTERNS` (`.env*`, `*.pem`, `*.key`, `id_rsa*`, `*secret*`, etc. — see `is_sensitive_filename`) and never follows symlinks. The filename still appears in the prompt so the commit message can mention it. Matters because the default model (`qwen3-coder:480b-cloud`) is proxied to Ollama's cloud.
- **Activity log redaction**: `activity_log.redact_credentials` masks URL-embedded credentials (`https://token@host` → `https://***@host`) in every entry's message/detail before buffering/writing — git echoes remote URLs (incl. PATs) in push/fetch errors.
- **Kiro provider**: the call is a plain argv list against the resolved `kiro-cli.exe` — no shell, no `bash -lc` string, so a settings/env-supplied model name is just an argument and cannot inject anything. (This replaced the old WSL path, where model name and temp path had to be `shlex.quote`d into a `wsl -- bash -lc` string.) The prompt goes over stdin rather than a temp file, so it never touches disk. Tests: `python tests/test_kiro_provider.py`.
- **gh token**: never written to disk; piped to `gh_workflow_viewer.py` via stdin (see Actions viewer above).
- Tests: `python tests/test_security.py` (symlink test self-skips without symlink privilege).
